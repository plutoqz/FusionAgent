## 2. 项目研究定位

项目名称/方向：FusionAgent。

研究背景是灾害情境下，在无人值守或少人干预条件下，实现受灾区域数据的快速产出。系统需要根据网络条件、时间条件和数据可得性，在不同策略之间做出选择：

- 如果网络和时间条件允许，且可以在可接受时间内产出融合数据，则调用既有融合算法完成多源数据融合。
- 如果不具备下载全部来源数据的网络或时间条件，则优先提供 OSM 等单源数据，保证先有可用数据；同时仍然启动完整融合流程，待融合完成后再提供融合后数据。

硕士研究重点不是提出新的融合算法，而是：

- 将既有融合算法、数据处理流程、评估方法拆解为可管理、可查询、可组合的知识。
- 将这些知识组织进灾害场景知识图谱。
- 验证知识图谱与 LLM 结合后，能否胜任并更好地胜任灾害场景下的数据生产、流程选择、任务解释和策略调整工作。

可能的后续扩展包括轨迹转道路、融合后数据质量评价等，但这些扩展同样应被定位为“将已有算法或方法沉淀到知识图谱中”，而不是把算法创新本身作为论文核心贡献。

## 3. 当前讨论形成的判断

此前对话中已经形成一个重要判断：原先系统中 LLM 的发挥空间可能偏小。如果 LLM 只是把用户请求转成固定参数、再调用确定性流程，那么论文中“LLM + 知识图谱”的必要性会显得不足。

用户认可“空间偏小”的判断，但希望保留 LLM，并倾向于扩大 LLM 的作用空间。

因此，下一步设计重点不是简单弱化 LLM，而是重新定义 LLM 在系统中的合理职责，让它承担更具有研究价值的工作，例如：

- 灾害场景意图理解：从模糊、紧急、非结构化需求中识别目标区域、任务优先级、可接受时延、数据质量要求等。
- 条件感知决策：结合网络、时间、数据源可用性、历史经验和知识图谱约束，选择“先单源后融合”或“直接融合”等策略。
- 知识图谱查询与解释：将图谱中的算法能力、输入输出约束、适用条件、失败条件、质量评价方法组织成可解释决策。
- 任务编排：不是让 LLM 直接执行融合算法，而是让它根据知识图谱选择、排序、解释和修正流程。
- 经验沉淀：将成功/失败案例、策略选择理由、数据质量结果沉淀回知识图谱，形成可复用证据。
- 人机交互解释：向用户解释为什么当前只能先产出 OSM 单源数据，为什么完整融合仍在后台继续，融合完成后数据如何替换或补充。

## 4. 建议的论文核心论点

可以把论文主线调整为：

> 面向灾害场景快速数据产出任务，构建一个融合灾害知识、数据源知识、算法能力知识与任务执行知识的知识图谱，并引入 LLM 作为场景理解、图谱查询、流程编排和解释交互的智能中枢，从而在网络/时间/数据条件不确定的情况下，实现可解释、可扩展、可无人值守的数据生产决策。

这个论点比“LLM 调用融合算法”更稳，因为它把研究贡献放在知识组织、决策机制、解释能力和系统闭环上，而不是放在已有融合算法本身。

## 8. 重要设计决策

建议保留以下设计方向：

- 融合算法作为外部能力或工具，不作为论文算法创新主体。
- 知识图谱保存算法能力、适用条件、输入输出、参数约束、质量评价、执行经验等知识。
- LLM 不直接替代算法，也不只做简单问答，而是承担场景理解、知识检索、任务规划、策略解释和经验沉淀。
- 系统要支持灾害场景下的渐进式数据交付：先有可用数据，再逐步提升数据完整性和质量。
- 对外表达时，应强调“灾害不确定条件下的数据生产决策与解释”，而不是只强调“自动调用融合算法”。
