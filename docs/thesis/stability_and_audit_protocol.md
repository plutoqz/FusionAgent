# Stability and Audit Protocol

Status: formal protocol frozen, formal runs not yet executed, 2026-07-20.

This document explains the machine-readable protocol in
`docs/thesis/stability_protocol.json` and the audit artifacts generated by
`scripts/run_product_contract_stability.py`.

## Formal Design

The frozen formal matrix contains:

```text
6 cases
x 5 baselines
x 5 repetitions
= 150 audited runs
```

Each case-planner pair receives input variants `0, 1, 2, 3, 4` exactly once.
The full schedule is shuffled with a fixed seed before execution. Gold remains
available only to post-planning evaluation and is never included in the
schedule, prompt, context, retry message, or provider request.

Formal mode requires:

- the complete frozen case and planner lists;
- exactly five repetitions;
- a clean Git worktree;
- `gpt-5.4-mini`;
- temperature `0.1`;
- JSON object response mode;
- the frozen common prompt and structured decision schema;
- at most one explicit grounding-repair retry.

Filtered, shortened, dirty-worktree, or otherwise exploratory runs are marked
`scope=development` and `claim_eligible=false`.

## Failure Policy

Failed runs remain failed observations. They are written to the audit ledger,
included in failure and repair rates, and excluded from successful-score
descriptive statistics. Scores are never imputed and deterministic fallback is
never substituted for a failed LLM result.

## Audit Chain

Every run produces one `StabilityAuditRecord` with:

- case, planner, repetition, and input variant;
- start/end timestamps and duration;
- commit, dirty flag, and implementation manifest hash;
- model, endpoint host, prompt/context hashes, token usage, latency, and retry
  count;
- evaluation metrics and normalized semantic decision signature on success;
- failure type and reason on failure;
- SHA-256 digest and size for every run artifact;
- `previous_record_hash` and `record_hash`.

Records are appended to `audit_ledger.jsonl`. The predecessor link and record
hash are verified before summaries or manifests are generated. Run artifact
directories are stored relative to the batch root so the complete batch can be
moved or archived without invalidating paths.

## Stability Statistics

For each planner and each case-planner group, the runner reports:

- success rate, failure rate, repair rate, and mean retry count;
- count, mean, median, sample SD, minimum, and maximum for every numeric metric;
- strategy mode agreement;
- pairwise Jaccard stability for priority precedence, initial delivery,
  background completion, not-delivered layers, and planner gap proposals;
- exact normalized decision-signature agreement.

With fewer than two successful runs, sample SD is `null` and pairwise semantic
stability is descriptive only.

## Batch Artifacts

```text
batch_metadata.json
protocol_snapshot.json
schedule.json
implementation_manifest.json
audit_ledger.jsonl
stability_summary.json
audit_manifest.json
runs/<run_id>/**
```

`--resume` verifies the existing chain and implementation manifest, skips
completed run IDs, and refuses to continue if implementation files changed.
Unaudited partial run directories are preserved with an `.orphaned.<timestamp>`
suffix before the run is attempted again.

## Commands

Development subset:

```powershell
python scripts/run_product_contract_stability.py `
  --scope development `
  --cases C02 `
  --planners fixed,kg_only,llm_only,llm_capability_kg,llm_full_contract_kg `
  --repetitions 2 `
  --output-dir <output-dir>
```

Formal matrix, after committing and verifying a clean worktree:

```powershell
python scripts/run_product_contract_stability.py `
  --scope formal `
  --output-dir <durable-output-dir>
```
